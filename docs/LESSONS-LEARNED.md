# tradex-hub 踩坑纪要（Lessons Learned）

> 记录开发/升级过程中**真实踩过**的坑，按主题归类。
> 每条格式：**现象 → 根因 → 对策**。
> 覆盖范围：v3.3.13 ~ v3.5.0（2026-09-14 ~ 09-19）及更早的典型问题。

---

## 0. 一句话总纲

**最危险的不是报错的代码，而是"看起来完全正常"的错数据。**

行数对、大小对、`/health` 绿、工具数 129 —— 这些**都不能证明结果正确**。
下面 90% 的坑，都属于"没有报错，但结果错了"。

---

## 1. 静默失败：最凶险的一类

### 1.1 降级链把"上游挂了"当成"成功返回空表"

- **现象**：某数据源接口稳定返回空表，既不降级到备源，健康度也不下降。
- **根因**：8 个 `fetch_fn` 写成 `except Exception: return pd.DataFrame()`。
  SmartRouter 拿到空 DataFrame 认为**调用成功**，于是不触发降级、不计失败。
- **对策**：**失败必须抛异常**，让路由层决定降级；"上游确实返回空"与"上游调用失败"是两件事，不能都用空表表达。
  单源失败属设计预期，用 debug 级日志留痕即可，但**不能吞成"成功"**。

### 1.2 按「位置」而非「字段名」映射列 → 整表语义全错

- **现象**：某接口返回 **615 行、84 KB**，HTTP 200、无异常 —— 但**每一列的语义都是错的**：
  `股票代码` 列里是市值 `-415345718.82`、`股票简称` 列里是代码 `000680`、持股变动列里是文本 `减仓`。
- **根因**：上游库用 `df.columns = [...]` **按位置**硬编码列名；上游东财改了字段顺序，整套映射错位。
- **对策**：
  1. 改为**按上游稳定字段名映射**（如 `SECURITY_CODE`），不要按位置；
  2. 该源改为**直取上游 JSON** 自行组装，绕开会失效的中间层；
  3. 加**数据形状守卫**：`股票代码` 列必须全是 6 位数字，否则抛错。
     **宁可失败，也不要把错标数据交给下游。**
- **教训**：只判"行数 > 0 / 非空"的验收，**漏得掉这一类 bug**。

### 1.3 兜底补丁打错了层

- **现象**：SSL 兜底逻辑写好了，却从未生效。
- **根因**：补丁 patch 的是 `urllib`，而目标库内部走 `requests`。
- **对策**：确认**真正被调用的那一层**再 patch；打完用日志验证它确实被走到。

### 1.4 排序键异常静默降级，污染回测首行

- **现象**：回测结果第一行数据异常。
- **根因**：`_bar_sort_key` 抛异常时静默返回默认值，把坏数据排到了首位。
- **对策**：收窄异常捕获范围；无法排序的记录返 `float('inf')` 排到末尾，并记 warning。

### 1.5 默认日期算出不存在的日期 → 恒空表

- **现象**：某接口**默认参数调用**永远返回空表。
- **根因**：按季推算出了 `20260631` 这种不存在的日期。
- **对策**：用真实月末计算（`_prev_quarter_end()` 一类），不要用固定 `31` 拼接。

## 2. 依赖与升级

| 坑 | 根因 | 对策 |
|---|---|---|
| 新环境安装即炸 | `mcp>=1.0.0` **无上限**，mcp 2.x 移除了 `mcp.server.fastmcp.FastMCP` | 依赖必须**设上限**：`mcp>=1.0.0,<2`（pyproject + requirements 两处同步） |
| 升级后功能报错 | 跨大版本移除了旧 API（如 `client.bars.all()`、`client.helpers.adjusted_kline()`） | 大版本升级前先做**调用面审计**（grep 提取真实调用点，逐个确认） |
| 补依赖漏项 | requirements.txt 缺运行时依赖 | 用"干净环境安装 + 跑一遍"验证，别只信开发机 |
| 并发下服务整个退出 | native（Rust/pyo3）库**非线程安全**，panic 抛 `PanicException` —— 它继承 **`BaseException`**，**不被 `except Exception` 捕获**，直接穿透杀穿事件循环 | ① 对 native 调用加**全局互斥锁**序列化；② 兜底改 `except BaseException`（但放行 `KeyboardInterrupt`/`SystemExit`/`CancelledError`） |

> ⚠️ **`except Exception` 抓不住进程级异常**（`BaseException` 系）。
> 服务端"干净退出、客户端永不重连"这类诡异现象，优先怀疑这个。

## 3. 并发与存储（SQLite）

| 坑 | 根因 | 对策 |
|---|---|---|
| `database is locked` | 建表函数里执行 PRAGMA，并发时争锁 | PRAGMA 抽到**独立连接**一次性设置 |
| 临时目录清理 PermissionError | `with conn` **只 commit 不 close**，WAL 文件被占用 | 用 contextmanager **显式 close**（必要时 `gc.collect()`） |
| 同毫秒并发撞主键 | 用毫秒时间戳做主键 | 主键加后缀：`{毫秒}-{线程ID}-{随机数}` |
| 迁移报 `no such table` | 迁移函数漏调建表 | 迁移**先建表再导数据**，保证幂等 |

> 📌 SQLite 在并发场景下，**连接生命周期必须显式管理**，不能依赖 `with` 的隐式行为。

## 4. 数据源与网络

| 坑 | 根因 | 对策 |
|---|---|---|
| 清了代理环境变量，请求仍走代理 | `requests.getproxies()` 是 `环境变量 or **Windows 注册表**`，空环境变量会**回退读注册表** | 显式设 `NO_PROXY=*` **短路**注册表读取 |
| 全量翻页接口稳定超时 | 默认单源超时 12s，而全量取数要翻 11 页 ≈ 17s（上游 `pageSize` 硬顶 500，调大无效） | 该类型在工具层**单独放宽超时**（如 40s） |
| 默认参数调用必挂 | 默认值恰好落在最慢那条路径 | 同上；并注意"无参调用"是用户最常走的路径 |
| 主备源"同生共死" | 主源与备源同属一家上游（同一接口族），一起挂 | 备源必须**跨上游厂商** |
| 降级链断裂 | 两源参数口径不同（`day/week/month` vs `daily/weekly/monthly`） | 加**归一化函数**，在边界处统一口径 |
| 每次调用白失败、污染健康分 | 上游已永久失效（返回 HTML 而非 JSON）但代码还在死磕 | 定期核对数据源健康度；失效源**退役**并换新源 |
| 大返回体撑爆上下文 | 全量接口动辄 800KB+，塞进对话会被判超限并落盘到不可读路径 | 探针脚本**就地解析、只打印摘要**（行数/首行/列名），不要回传原始体 |

## 5. MCP 协议与长驻进程

### 5.1 streamable-http **默认有状态** → 服务重启即客户端失联

- **现象**：客户端报 `Session not found`；表现为"时断时连"。
- **根因**：传输层默认在**服务端内存**维护 session 表，客户端持有 `Mcp-Session-Id`；
  服务端一重启（或被守护进程重启），内存表清空 → 旧 id 全废。
- **对策**：服务端开启 **无状态模式**（`FastMCP(..., stateless_http=True)`）。
  每个请求自带完整上下文，**服务端重启对客户端完全透明**。

> 💡 这是"常驻服务型 MCP"的通用解法：**服务端无状态，客户端才免疫重启。**

### 5.2 长驻进程的代码是"冻结"的

- **现象**：磁盘源码已改，行为却没变。
- **根因**：Python 模块 import 进内存后即固化，**活进程仍跑旧代码**。
- **对策**：改代码后**必须重启进程**；验证要用**行为探针**（调那个改动的入口，比对预期差异），
  不要看版本号——MCP 协议层通常**没有暴露服务端版本的工具**。

### 5.3 缓存会掩盖修复效果

- **现象**：修复后调用仍返回旧结果。
- **根因**：工具层缓存 key 含参数，用**同一组参数**会命中旧缓存。
- **对策**：验证时**换一个全新的参数组合**，绕开缓存。

### 5.4 "工具搜不到"先查配置，别怪代码

- **排查顺序**：① 服务是否被**禁用**（配置里的 `disabled`）→ ② 进程是否存在 → ③ 启动日志有无报错 → ④ 最后才怀疑代码版本。

## 6. Windows / 跨平台

| 坑 | 根因 | 对策 |
|---|---|---|
| 批处理报"命令语法不正确" | 文件是 **LF 换行**；cmd 对 LF-only 的 `goto`/标签/`if` 块解析异常 | 批处理**必须 CRLF**（写完做字节级校验：`count('\r\n') == count('\n')`） |
| 从脚本调 `cmd.exe` 全部命令报语法错误 | 用了**正斜杠**路径（`C:/Windows/System32/cmd.exe`） | Windows 可执行路径用**反斜杠** |
| 状态文件在不同会话"丢失" | 用 `%TEMP%` 定位状态文件，而 **SYSTEM 会话**与**用户会话**的 `TEMP` 不同（`C:\Windows\Temp` vs 用户目录） | 状态文件（锁文件等）用**固定绝对路径**，不要依赖环境变量 |
| 文件被占用，删不掉 | 有未关闭的句柄（如 SQLite WAL） | 显式关闭连接；确认无残留句柄 |

## 7. 验证方法论：怎么才敢说"修好了"

1. **不只判"行数/非空"** —— 必须**打印前 2~3 行的真实取值**，逐列自问"这个值放在这个列名上说得通吗"。
2. **看返回体长度**（免费信号）：失败通常是**极短字符串**（~60 字符），成功是**整包体**（数百 KB）。
   量级跳变基本可判修复生效 —— 但仍需逐列校验才算收口。
3. **对比"磁盘代码"与"服务端行为"**：用行为探针跑**同一个新参数**，两边比对。
4. **换参数避开缓存**再下结论。
5. **大返回体不要进对话**，就地解析只打摘要。
6. **加数据形状守卫**：让"错数据"变成"响亮的异常"，而不是"安静的错误"。
7. **改完就跑回归**，并记录通过数基线（每个版本都要能对上）。

## 8. 通用规律（最值得记住的 5 条）

1. **静默的错 > 响亮的错。** 宁可抛异常，也别返回"看起来正常"的错数据。
   所有"吞异常 + 返回默认值/空值"的写法，都要重新审视。
2. **"看起来正常"是最大的陷阱。** 行数、大小、健康检查、工具数量，**都不能证明正确**。
3. **平台/会话差异是暗礁。** Windows 的换行与文件占用、SYSTEM 与用户会话的 `%TEMP%`。
4. **长驻进程有陈旧状态。** 内存里冻结的代码、内存里的 session 表、残留的锁文件。
5. **并发是无声杀手。** 同毫秒主键、PRAGMA 争锁、native 库非线程安全 —— 都不报错，只是偶尔错。
